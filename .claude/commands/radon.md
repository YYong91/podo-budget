Radon 코드 품질 스캔을 실행하고, 결과를 분석하여 필요 시 GitHub 이슈를 생성한다.

## 실행 순서

### 1단계: Radon 스캔
```bash
cd $PROJECT_ROOT
.venv/bin/python scripts/radon_scan.py --json
```

결과 JSON을 읽고 아래 기준으로 분석한다.

### 2단계: LLM 판단 (각 고복잡도 함수에 대해)

diff 결과에서 **악화(worsened)** 또는 **신규(new_issues)** 항목만 대상으로:

1. 해당 함수의 소스코드를 읽는다
2. 다음을 판단한다:
   - 리팩토링이 필요한가? (복잡도가 높지만 정당한 이유가 있는 경우 제외)
   - 어떻게 분리하면 좋은가? (구체적 제안)
   - 우선순위는? (P0~P2)

판단 기준:
- 웹훅 dispatch 함수처럼 분기가 본질적으로 많은 경우 → "수용 가능" 판정
- 하나의 함수가 여러 책임을 지는 경우 → 리팩토링 대상
- CC가 15 이상이면서 테스트가 없는 경우 → 높은 우선순위

### 3단계: 액션

**리포트만 (기본):**
- 스캔 결과 요약을 사용자에게 보여준다
- 변화가 있으면 변화 내역도 함께 보여준다

**이슈 생성 (사용자가 요청 시):**
리팩토링이 필요하다고 판단된 함수에 대해 GitHub 이슈를 생성한다:

```bash
gh issue create \
  --title "[리팩토링] {파일명}:{함수명} 복잡도 개선 (CC={복잡도})" \
  --label "code-quality" \
  --body "이슈 본문"
```

이슈 본문에 포함할 내용:
- 현재 복잡도와 등급
- 해당 함수가 하는 일 요약
- 구체적인 리팩토링 제안
- 예상 효과 (목표 복잡도)

**기존 이슈 업데이트:**
이미 해당 함수에 대한 이슈가 있는 경우, 코멘트로 복잡도 변화를 기록한다.

### 4단계: 프로젝트 상태 업데이트

## 주의사항

- .radon/history.json은 git에 포함하지 않는다 (.gitignore에 추가됨)
- 첫 실행 시에는 비교 대상이 없으므로 모든 항목이 "신규"로 표시된다
- 이슈 생성 전에 반드시 사용자에게 확인을 받는다
- `$ARGUMENTS`에 `--issues`가 있으면 이슈 생성 모드, 없으면 리포트만
